# H4 (Proponent): A versioned conformance profile + test-vector suite is sufficient for cross-node deterministic Wasm execution

SUPPORT STRENGTH: moderate — The literature strongly establishes the two preconditions H4 needs: (1) Wasm has a precise, mechanized semantics that makes a "profile" a well-defined mathematical object, and (2) the nondeterminism in Wasm is small and enumerable, so it can be pinned by configuration. The weaker link — that *passing a test suite* implies *behavioral equivalence across engines* — is only closed when the test oracle is itself backed by a verified semantics. The corpus shows that exact tool exists and is industrially deployed (WasmRef-Isabelle), which is what lifts this from "weak" to "moderate." It falls short of "strong" because no cited paper proves the full chain "engine passes suite ⟹ engine is deterministic-equivalent to the spec," and the same papers document live engine bugs that a finite suite would not necessarily catch.

This document builds the strongest honest case FOR H4. The falsifier brief addresses the residual gap.

---

## 1. Why a "profile" is a well-defined object, not a vibe

H4 presupposes that "conformance profile" denotes something precise enough to be enforced. Three results in the corpus establish that Wasm — uniquely among mainstream bytecode VMs — has a single, mathematical source of truth that a profile can reference.

**Mechanising and verifying the WebAssembly specification** (Watt, 2018; DOI 10.1145/3167082) (abstract only). This is the foundational result: the Wasm working group "incorporated formal techniques into the development of the language," and this paper mechanizes the pen-and-paper spec in Isabelle/HOL, proving the type-soundness properties (progress and preservation) that the language was designed around. The significance for H4 is structural: the meaning of a Wasm program is not defined by "whatever the reference engine does" (the situation for the EVM or the JVM in practice) but by an operational semantics that has been transcribed into a proof assistant and machine-checked. A "conformance profile" can therefore be defined as *a subset of this semantics with specific nondeterministic choices fixed*, which is a precise mathematical statement rather than an informal agreement.

**Wasm SpecTec: Engineering a Formal Language Standard** (Breitner et al., 2023; DOI 10.48550/arxiv.2311.07223) (full text). SpecTec sharpens this further by making the formal semantics the *single source of truth* from which every other artefact is mechanically derived. The paper states that standardizing any Wasm feature requires four artefacts — "a formal (mathematical) specification ... a prose pseudocode description ... an implementation in the official reference interpreter, and a suite of unit tests" (abstract) — and SpecTec generates all of them from one DSL definition. Crucially, the same source generates *both* the LaTeX semantics, the executable AL interpreter, prover backends (Coq/Isabelle/Agda/Lean), and "Test Suite / Fuzzer" outputs (Figure 1, §2). This is the precise mechanism H4 needs: the test-vector suite and the formal semantics are not independent artefacts that might drift; they are co-generated from one definition. A versioned profile pinned to a SpecTec version is pinned to a mathematically defined semantics *and* to a test suite that provably reflects it. The paper also directly endorses the suite's purpose: "the insistence on a comprehensive test suite for each newly added feature further guarantees that various implementations of Wasm exhibit consistent behavior ... serve to reduce the risk of implementation divergence" (§2). That is H4's thesis stated by the language's own standards engineers.

**Iris-Wasm: Robust and Modular Verification of WebAssembly Programs** (Rao et al., 2023; DOI 10.1145/3591265) (abstract only). Iris-Wasm builds a mechanized higher-order separation logic on "a specification of Wasm 1.0 mechanized in Coq" and proves *robust safety* — "unknown, adversarial code can only affect other modules through the functions that they explicitly export," "demonstrating that WebAssembly enforces strong isolation between modules" (abstract). For H4 this matters because cross-node determinism can be broken not only by arithmetic but by *isolation leaks*: if module A could observe host or sibling state through an unsanctioned channel, two engines could diverge on identical inputs. Iris-Wasm gives a machine-checked argument that the only legitimate inter-module influence is through declared exports, narrowing the surface a profile must control to the explicitly declared interface and the host's import set — both of which a profile pins.

Together these three give H4 its first pillar: the profile references a real, mechanized, isolation-proven semantics, so "conformance to the profile" is a well-typed proposition.

## 2. Why Wasm's nondeterminism is small and enumerable — so it can be pinned

H4's second precondition is that determinism is achievable *by disabling a finite set of features and pinning a fuel schedule*, rather than by chasing unbounded engine differences. The corpus supports the claim that Wasm was *designed* to be deterministic modulo a short, enumerable list.

The motivating history in **Wasm SpecTec** is explicit about why determinism is the design goal and where divergence historically comes from: "historically Web languages have been particularly vulnerable to issues of implementation discrepancy ... discrepancies may occur inadvertently simply due to the number of different browser implementations ... each one in itself consisting of several tiers of interpretation and just-in-time compilation. ... Portability is only feasible if implementations are meticulous in aligning their behaviours" (§1). The entire artefact regime — formal spec + reference interpreter + test suite — exists precisely to suppress this divergence. The paper reports the concrete payoff: the SpecTec-extracted semantics "passed all 23,778 tests (SIMD excluded) in the test suite" (§2). A suite of that density over a language that small is a strong fingerprint of the intended behavior.

The known sources of legitimate nondeterminism in core Wasm are a short list, and each is a configuration knob a profile can fix:
- **Floating-point NaN bit patterns** — the one classic source of value-level nondeterminism. The corpus shows the arithmetic semantics are fully pinned-down enough to mechanize: WasmRef-Isabelle "fully mechanise[s] the numeric semantics of WebAssembly's integer operations," and SpecTec's worked example is precisely the `binop` execution rule, where the result is determined by the auxiliary function `$binop(binop, nt, c_1, c_2)` (Figures 3–6). A profile that mandates canonical NaN propagation (a documented spec option) removes the only value-level wobble.
- **Resource exhaustion / stack and memory limits** — divergence here is about *when* a trap fires, not what the result is. This is exactly the "fuel schedule" lever in H4: pinning the fuel/gas accounting makes the trap point a deterministic function of the program, not of the host's available memory. A pinned fuel schedule converts an environmental nondeterminism into a profile constant.
- **Excluded features** — `threads`/shared-memory concurrency and SIMD are the features that introduce genuine cross-engine observability differences (relaxed-SIMD lanes are deliberately implementation-defined). The corpus confirms these are *separable*: SpecTec evaluated everything "except for the recently-standardized SIMD vector instructions" and still covered all of Wasm 2.0, demonstrating that the deterministic core is a clean subset you can profile in isolation. H4's profile simply disables the nondeterministic features — exactly the enumerable list above.

So the "disable a small set + pin a fuel schedule" prescription in ADR-005 maps one-to-one onto the known nondeterminism sources in the mechanized semantics. This is the mechanism that makes H4 plausible rather than aspirational.

## 3. The crux: why a *verified-semantics-backed* suite closes the "passes tests ≠ equivalent" gap

The honest objection to H4 is the standard one about testing: a program can pass a finite suite and still diverge on an untested input. A profile pinned to *just* a fixed corpus of `.wast` vectors is necessary but not obviously sufficient. The corpus contains the result that materially shrinks this gap.

**WasmRef-Isabelle: A Verified Monadic Interpreter and Industrial Fuzzing Oracle for WebAssembly** (Watt et al., 2023; DOI 10.1145/3591224) (abstract only). This is the keystone for H4's sufficiency claim. WasmRef-Isabelle is "a monadic interpreter for WebAssembly written in Isabelle/HOL and proven correct with respect to the WasmCert-Isabelle mechanisation of WebAssembly" via "a two-step refinement proof." Critically, it is not a lab artefact: it "has been adopted and deployed as a fuzzing oracle in the continuous integration infrastructure of Wasmtime, a widely used WebAssembly implementation" (abstract).

This changes the epistemics of "passing a test suite" in three ways:

1. **The oracle is the semantics, not a sample.** Conformance is no longer "does engine E reproduce N hand-written vectors?" but "does engine E agree, on fuzzer-generated inputs, with an interpreter that is *proven equivalent to the mechanized formal semantics*?" Differential fuzzing against a verified oracle effectively turns the finite suite into an open-ended, semantics-defined check. Every new fuzzer input is a fresh conformance vector whose expected answer is, by the refinement proof, the spec's answer — so the suite is unbounded and provably correct, not a fixed list someone might overfit.

2. **It was adopted *because* the alternative oracle was unsound-in-practice.** The paper records that "previous efforts to fuzz Wasmtime against WebAssembly's official OCaml reference interpreter were abandoned ... after the reference interpreter exhibited unacceptable performance characteristics." The verified interpreter "achieve[s] the best of both worlds — an interpreter fast enough to be useable as a fuzzing oracle that also maintains a close correspondence with the specification." This is direct industrial evidence that a *verified-semantics-backed* conformance check is both deployable and is the chosen mechanism for catching engine divergence in a production Wasm engine — exactly the enforcement vehicle H4 relies on.

3. **The numeric core is fully nailed down.** Because WasmRef-Isabelle "fully mechanise[s] the numeric semantics of WebAssembly's integer operations," the one part of execution most prone to silent cross-engine divergence (off-by-one in shift/rotate/division-by-zero trapping behavior) is checked against a proven-correct reference, not a peer engine that might share the bug.

The argument for H4, then, is: a profile that (a) references a versioned mechanized semantics (Watt 2018; SpecTec), (b) disables the enumerable nondeterministic features and pins a fuel schedule (§2), and (c) is *enforced* by differential testing against a verified oracle in the WasmRef-Isabelle style (rather than against a static vector dump) gives a check whose passing input set is co-extensive with the semantics, not a finite sample of it. Under that enforcement model, "passes the profile's test regime" approaches "behaves as the pinned semantics dictates," which is precisely cross-node determinism.

## 4. Supporting context: the deterministic-subset discipline generalizes

**CT-wasm: type-driven secure cryptography for the web ecosystem** (Watt et al., 2019; DOI 10.1145/3290390) (abstract only) is corroborating evidence that *restricting Wasm to a well-typed, verified subset to obtain a strong behavioral guarantee* is an established, mechanized pattern. CT-Wasm is "a type-driven, strict extension to WebAssembly" whose "type system ensures that code ... is both information flow secure and resistant to timing side channel attacks," with "these guarantees ... verifiable in linear time," built "on an existing Wasm mechanization" with a "verified type checker." The relevance to H4 is by analogy of method: CT-Wasm shows that a *profile-like* restriction (a typed sublanguage) layered on the mechanized semantics can deliver a property (constant-time, here) that the base language does not universally guarantee, and that the restriction is *cheaply and statically checkable*. H4's determinism profile is the same move applied to nondeterminism: pin a subset, and a linear-time/conformance-time check enforces the property. CT-Wasm is existence-proof that the "profile on top of mechanized semantics" architecture yields enforceable cross-engine guarantees.

## 5. Honest statement of the residual gap (and why it is narrow)

To weight this honestly:

- **No cited paper proves the closing theorem** "for all engines E, E passes profile-P's test regime ⟹ E is observationally equivalent to semantics-P on all P-conformant inputs." The corpus gives the *ingredients* (mechanized semantics, verified oracle, enumerable nondeterminism) but not that end-to-end statement. H4 says "sufficient to guarantee"; the literature supports "sufficient to make divergence vanishingly unlikely under verified-oracle enforcement," which is strong but is a probabilistic/coverage claim, not a proof of universal equivalence.

- **Fuzzing finds bugs, which means engines diverge from the spec in the wild.** WasmRef-Isabelle exists *because* Wasmtime needed continuous fuzzing to catch divergences — implying real engines do diverge until caught. A profile + suite is only as good as the fuzzing campaign behind it; a *static* vector suite (H4 read literally as "test-vector suite") is weaker than the live verified-oracle fuzzing the corpus actually validates. The strong form of H4 therefore depends on the profile mandating verified-oracle differential testing, not merely shipping a frozen `.wast` corpus.

- **Coverage of excluded features must be enforced, not assumed.** SpecTec's own evaluation set aside SIMD; relaxed-SIMD and threads are exactly the divergence-prone areas. The profile's *exclusion list* is load-bearing and must be enforced at module-validation time (the kind of static check Iris-Wasm/CT-Wasm show is feasible), or excluded nondeterminism leaks back in.

Why the gap is narrow rather than fatal: the residual risk is concentrated entirely in the *enforcement mechanism's coverage*, not in the *definition* of the profile. The profile is mathematically well-defined (pillar 1), the nondeterminism it must suppress is finite and known (pillar 2), and an industrially-deployed, proof-backed enforcement oracle for exactly this purpose exists (pillar 3). That is a far stronger footing than any other production VM ecosystem in the corpus, and it justifies "moderate" support for the engineering claim, trending toward strong *if and only if* ADR-005 commits to verified-oracle differential conformance (WasmRef-Isabelle style) rather than a static vector dump.
