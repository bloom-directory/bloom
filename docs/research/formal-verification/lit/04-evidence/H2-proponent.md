# H2 Proponent — Runtime detection ≠ prevention for the logic-bomb class

SUPPORT STRENGTH: strong — The literature consistently frames pure runtime checks as trace-local observations whose firing is conditioned on the program *reaching* the checked state, while prevention of a guarded logic bomb provably requires quantifying over unexecuted paths (symbolic/static reasoning) before deployment. The strongest apparent counterexample — Theorem-Carrying Transactions — does not refute H2; on inspection it *confirms* the mechanism, because its prevention guarantee comes from per-transaction *symbolic* proof obligations, not from observing reached state, and its own design treats an unseen guarded path as a repo-miss requiring a fresh proof or a revert.

---

## H2 restated (claim under test)

A pure view-function invariant evaluated at runtime is a *state-observation* mechanism: it can only evaluate predicates over states the execution actually reaches. A logic bomb gated on an un-triggered input lives on an unexecuted branch; until that branch is taken, the malicious state transition never materializes, so a runtime observer is *structurally blind* to it. Prevention therefore requires reasoning that quantifies over the *unexecuted* state space ahead of time — static proof or symbolic path reasoning. Fuzzing does not close this gap categorically: it is *sampling* the input/state space, and its probability of triggering a narrow guard is bounded (roughly) by the measure of the guarded branch. Hence: runtime detection ≠ prevention.

This decomposes into three sub-claims, each supported below:
1. **(Mechanism of runtime checks)** A runtime check is trace-local — it fires only on reached states.
2. **(Fuzzing as bounded sampling)** Random/coverage-guided input generation misses sparse-guard branches with probability tied to the guard's measure.
3. **(Prevention requires ahead-of-time quantification)** Only symbolic/static reasoning over unexecuted states certifies absence of the bomb.

## Evidence for sub-claim 1: runtime checks are trace-local observations

**Runtime Verification of Ethereum Smart Contracts** (Ellul & Pace, 2018; DOI 10.1109/edcc.2018.00036) (abstract only). The paper's foundational framing is the standard RV one: monitors are synthesized from specifications and evaluated against the *execution trace* the contract actually produces. RV by construction observes what happened; it instruments the running system. This positions runtime monitoring as a dynamic, trace-driven activity — exactly the "state-observation" character H2 attributes to a view-function invariant. (Quality: directly on-domain — Ethereum RV — but cited from abstract/title framing only, so weighted as corroborating rather than decisive.)

**A survey of challenges for runtime verification from advanced application domains (beyond software)** (Bartocci et al., 2019; DOI 10.1007/s10703-019-00337-w) (full abstract). The survey defines RV precisely as "the dynamic analysis of execution traces against formal specifications," whose core activities are "creating monitors from specifications" and "the evaluation of traces against the generated monitors." This is an authoritative, definitional statement that RV operates over *traces that occur*. A monitor that never sees the guarded transition cannot evaluate any predicate on it. The survey's emphasis on "instrumentation of the system to generate the trace" reinforces that the monitor's input is reached behavior, not the latent unexecuted branch. (Quality: high — a peer-reviewed survey giving the field's own definition; the load-bearing content is in the abstract.)

**Runtime Assertion Checking and Static Verification: Collaborative Partners** (Maurica, Cok & Signoles, 2018; DOI 10.1007/978-3-030-03421-4_6) (abstract/title only). The title itself encodes H2's central thesis: RAC and static verification are framed as *collaborative partners*, i.e., complementary rather than substitutable. The collaboration is necessary precisely because each covers what the other cannot — runtime assertion checking certifies the concretely executed path, static verification discharges obligations over all paths. The paper's existence as a "collaborative partners" argument is itself evidence that the field does *not* treat runtime checking as a replacement for ahead-of-time proof. (Quality: moderate — title-level framing, used to establish the field's complementarity stance, not for internal technical detail.)

Together these establish the mechanism cleanly: a runtime invariant is an observer of reached states and must be *paired with* (not substituted by) static methods.

## Evidence for sub-claim 2: fuzzing is bounded sampling, weak on narrow guards

**Are We There Yet? Unraveling the State-of-the-Art Smart Contract Fuzzers** (Wu et al., 2024; DOI 10.1145/3597503.3639152) (abstract only — full text was paywalled/403 in the corpus). This SoK exists *because* "a systematic investigation of smart contract fuzzing techniques remains lacking" and proceeds to "evaluate state-of-the-art contract fuzzers' usability" against "a carefully-labeled benchmark" using "pragmatic performance metrics" from "five complementary perspectives," explicitly providing "direction for future research and development." The framing concedes that current fuzzers have measurable usability and coverage gaps and are still maturing — i.e., fuzzing is an empirical detection technique with non-trivial miss behavior, not a soundness guarantee. (Quality: high venue (ICSE'24), directly on-domain; but cited from abstract only, so the *quantitative* miss rates are not available to me and I do not assert specific numbers.)

**Coverage guided, property based testing** (Lampropoulos et al., 2019; DOI 10.1145/3360607) (full abstract). This is the cleanest mechanistic statement of the miss-probability argument in the corpus. The paper observes that property testing "works very well in many cases, but not always": specifically, "Some properties are conditioned on the input satisfying demanding semantic invariants that are not consequences of its syntactic structure," and crucially, "Most randomly generated inputs fail to satisfy properties with such *sparse preconditions*, and so are simply discarded." A logic bomb gated on a specific un-triggered input value is exactly a *sparse precondition*: the set of inputs that reach the guarded branch has small measure, so random sampling almost surely lands outside it. The authors propose coverage guidance precisely to mitigate (not eliminate) this — confirming that absent such targeting, the miss probability tracks the guard's measure, and even with it the guarantee remains probabilistic. (Quality: high — peer-reviewed PL venue; directly states the H2 fuzzing-as-sampling mechanism in general terms.)

**Almost correct invariants: synthesizing inductive invariants by fuzzing proofs** (Lahiri & Roy, 2022; DOI 10.1145/3533767.3534381) (abstract/title only). Notably, this work uses fuzzing to *synthesize candidate inductive invariants* that are then handed to a proof engine — i.e., fuzzing supplies guesses and the *inductive* (all-states) guarantee comes from the proof step. The very architecture (fuzz to propose, prove to discharge) embodies H2's division of labor: sampling cannot certify universally, so it is wrapped by symbolic reasoning. An "almost correct" invariant is precisely one that sampling endorsed but that requires proof to make sound — a direct illustration that detection-style evidence is not prevention-grade evidence. (Quality: moderate — title/venue-level inference, used as structural corroboration of the fuzz-proposes/prove-disposes pattern, not for internal results.)

The mechanism: fuzzing's coverage of the input space is a measure-bounded sample; a narrow guard is a low-measure target; therefore the trigger is missed with probability close to 1 unless the guard's structure is somehow inferred — which returns the problem to static/symbolic analysis.

## Evidence for sub-claim 3: prevention requires quantifying over unexecuted states

The static/symbolic verification literature in the corpus provides the contrasting capability — reasoning over *all* admissible states, including unreached ones. **VerX: Safety Verification of Smart Contracts** (Permenev et al., 2020; DOI 10.1109/sp40000.2020.00024) (full text) performs *automated* verification of temporal safety properties for all reachable states via symbolic execution + predicate abstraction, establishing properties that hold "for every execution" rather than for an observed trace. **Fast and Reliable Formal Verification of Smart Contracts with the Move Prover** (Dill et al., 2022; DOI 10.1007/978-3-030-99524-9_10) (full text) discharges specifications as SMT proof obligations that quantify universally over inputs and states. These are the kind of ahead-of-time, universal guarantees a runtime observer cannot produce: a proof that no admissible input drives the contract into the bomb's malicious post-state is a statement about *unexecuted* paths. (Quality: high — both peer-reviewed, full text available; cited here to instantiate "what prevention looks like," consistent with H2.)

## The strongest counter, engaged honestly: Theorem-Carrying Transactions (TCT)

**Theorem-Carrying Transactions: Runtime Verification to Ensure Interface Specifications for Smart Contract Safety** (Ball, Bjørner, A. Chen, S. Chen, Y. Chen, Guo, Hsu, Liu, Luo, 2024/2025; arXiv:2408.06478v2) (full text). TCT is the genuine threat to H2 because it is a *runtime*-branded mechanism that *prevents* before commit: "every transaction must carry a theorem that proves its adherence to the properties in every contract to be executed... The runtime platform checks the validity of the theorem **before allowing the transaction to be executed**" (§1). A transaction that would violate the invariant is *reverted* — "a transaction is either completed or reverted. Reversion means that the program state remains unchanged" (§2.1). So pre-commit reverts plainly *do* prevent the malicious state transition from being committed. Does this defeat "detection ≠ prevention"?

**No — and the reason is exactly H2's mechanism.** Three observations from the TCT text:

1. **TCT's prevention comes from *symbolic* reasoning, not state observation.** TCT explicitly contrasts itself with a "simple runtime assertion," which is "concretely checked when the line is reached" (§1, lines 144–148). It states that the properties it ensures "require symbolic reasoning... which is traditionally done by static verification. TCT is designed to have the same symbolic-reasoning capability as static verification" (§1). The theorem it checks is `φ ⇒ VC(ct)` — the guard implies the *verification condition of the entire straight-line code trace*, proven by Boogie (§4, `AddTheorem`). That is a quantifier over all variable valuations consistent with the path (§3.2: "Because all variables are symbolic, a proven theorem has the generality to cover all future transactions that follow the same code trace"). This is precisely the "quantifying over unexecuted states before deployment (static proof / symbolic reasoning)" that H2 says prevention requires. TCT is therefore *evidence for* H2's prevention mechanism, not against it. A *pure view-function invariant* — the actual object of H2 — has no such symbolic capability; TCT had to add a concolic executor and an SMT proof to acquire it.

2. **TCT itself treats the un-triggered/unseen guarded path as the danger boundary, and handles it by proof or revert — not by observation.** The reentrancy case study (§3.2, lines 503–528) is a logic-bomb-shaped scenario: the benign guard `φ := (0 ≤ totalSupply < 2²⁵⁵) ∧ (_to ≠ msg.sender)` is "sufficient to ensure the invariants" for the *non-reentrant* path, but "if the transaction exploits the reentrancy pattern... the code path is different... the theorem for the non-reentrancy transaction is not applicable to the reentrancy one, because of the path hash mismatch." The authors are explicit that "the programmer is unlikely to anticipate the reentrancy code path." TCT survives *not* because a runtime observer caught the bomb, but because **a transaction taking the unanticipated path is a repo-miss, and a repo-miss requires a freshly proven theorem before it may commit** (§4: "When there is no applicable theorem (i.e., a repo miss)... the user needs to provide a guard φ" and the transaction may only proceed "if the theorem is proven"). The attacker can only commit by proving a theorem about *their* path; for the malicious path the natural guard "will fail the proof," and the only guard that proves (`balances[msg.sender] = 0`) renders the attack "a no-op." The prevention is again the *symbolic proof obligation over the new path*, discharged ahead of execution-commit — not state observation of a reached invariant.

3. **TCT relocates, but does not abolish, the ahead-of-time quantification.** Its low overhead depends on theorems being "pre-populated in E.T during the testing phase" for "the scenarios [programmers] can imagine" (§4). For a deliberately *hidden* logic bomb whose guard the honest programmer never imagines, no pre-populated theorem exists; the bomb's transaction is a repo-miss. At that boundary TCT's safety reduces to: *either* someone discharges a symbolic proof that the path preserves the invariant (which a real bomb cannot, if the invariant captures the harm), *or* the transaction is rejected. In both branches the decisive act is symbolic reasoning over a previously unexecuted path — performed *before* commit. TCT is thus a *constructive instance* of H2's thesis ("prevention requires quantifying over unexecuted states"), implemented as a pre-commit gate, rather than a counterexample to it.

**Residual honesty / scope of the win.** TCT does show that the *prevention boundary can be pushed to transaction-commit time* (post-deployment, pre-state-mutation) rather than strictly pre-deployment, *provided* the safety-relevant harm is fully captured by an interface specification (invariant/postcondition) and *provided* the platform itself runs the TCT protocol. This is a real qualification to a naïve reading of "prevention requires pre-deployment proof." But it does not rescue the *pure view-function invariant* that H2 targets: (a) a view function returning a boolean over current state performs no symbolic proof and reverts nothing by itself; (b) TCT explicitly distinguishes itself from such assertions; (c) TCT's guarantee is "only as high as the safety specifications go" (§1) — if the invariant does not encode the bomb's harm, neither TCT nor any runtime observer prevents it, which again throws the burden onto *specifying and proving over unexecuted states*. For the logic-bomb class as defined in H2, detection ≠ prevention holds.

The case is **strong** because the single most threatening counterexample (TCT) is, on its own text, an implementation of H2's prescribed remedy: it prevents the logic-bomb class precisely by attaching symbolic proofs that quantify over each (possibly first-seen) code path before commit, and it explicitly disclaims the bare runtime assertion / view-function invariant as inadequate to that task. Pure runtime observation detects reached states; preventing an un-triggered guarded bomb requires symbolic reasoning over the unexecuted path — pre-deployment in general, or at latest as a pre-commit proof gate as in TCT. ADR-002's distinction stands.
